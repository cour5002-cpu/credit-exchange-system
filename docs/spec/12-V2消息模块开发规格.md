# V2 消息模块开发规格

## 1. 文档状态

| 项目 | 内容 |
|---|---|
| 版本 | V2.0 设计冻结版 |
| 冻结日期 | 2026-08-08 |
| 适用范围 | V2 站内消息模块 |
| 稳定规格 | 本文 |
| 决策过程记录 | 本地开发过程资料，不作为仓库正式规格发布 |

本文是 V2 消息模块的稳定开发契约。开发过程中如需改变事件、收件人、字段、接口或事务语义，必须先更新本文并完成评审，不能只修改代码。

## 2. 建设目标与边界

### 2.1 本期目标

- 为学生、指导老师、审核老师和管理员提供统一站内消息收件箱。
- 在已经确认的业务状态变化后，向明确的收件用户生成消息。
- 支持消息列表、详情、未读数量、单条已读、批量已读和全部已读。
- 支持管理员向全部正常用户或指定角色发布系统公告。
- 消息按学年、学期长期保存和查询。
- 为未来企业微信通知保留服务边界，但不提前建设企业微信投递能力。

### 2.2 本期不做

- 不接入企业微信、短信或邮件。
- 不使用 WebSocket、Redis、消息队列或异步投递任务。
- 不提供普通用户、前端管理员删除消息的接口。
- 不允许普通调用方通过通用接口伪造业务消息。
- 不提供已读恢复为未读。
- 不做消息重要等级；前端只按消息类别使用不同视觉标识。
- 不做业务分类筛选界面；V2 只提供全部、已读、未读筛选。
- 不为消息复制或永久保存业务附件。
- 不提前增加企业微信渠道、投递状态、失败重试字段。

## 3. 核心业务规则

### 3.1 消息不是业务事实来源

业务状态以任务、课时、延期、投诉、申诉、学分兑换和规则文件等原业务表为准。消息只保存用户可读的通知快照，不得通过编辑消息反向改变业务状态。

### 3.2 一人一条消息

每个收件人对应一条 `notifications` 记录。团队或公告有多个收件人时，为每个收件用户分别创建记录，以便独立维护权限和 `read_at`。

### 3.3 收件账号条件

- 新消息只投递给 `users.status = "active"` 且未被删除的账号。
- 临时登录锁定不改变账号有效状态，仍可投递。
- 停用、注销、软删除账号不接收新消息。
- 账号停用前的历史消息继续保留。
- 规则更新和公告按触发时刻的有效账号、角色快照计算收件人；以后角色变化不追溯增删历史消息。

### 3.4 阅读规则

- 数据库只保存 `read_at`；`read_at IS NULL` 表示未读。
- API 同时返回计算字段 `is_read` 和时间字段 `read_at`。
- 第一次标记已读时写入 `read_at`，重复调用不覆盖第一次阅读时间。
- 不允许恢复未读。
- GET 列表和详情均不得隐式改变阅读状态。
- 全部已读必须携带客户端当前已见的 `up_to_id`，只更新当前用户且 `id <= up_to_id` 的消息。

### 3.5 生命周期规则

- 普通消息长期保留，不因已读、学期切换或账号停用自动删除。
- “归档”指默认不展示其他学期，不代表删除或迁移数据。
- 默认查询当前学期；切换学年、学期后可以查询历史消息。
- 创建消息时保存 `academic_year`、`semester` 快照，旧消息不随系统配置变化重新归类。
- 产品不提供删除接口。特殊纠错、违法内容或合规删除由运维执行受控脚本，并保留审计和删除前备份。

## 4. 消息分类与事件目录

### 4.1 固定分类

| category | 中文含义 | 前端视觉用途 |
|---|---|---|
| `task` | 任务发布、报名、取消 | 任务类别标识 |
| `hour_application` | 课时申请与审核结果 | 课时类别标识 |
| `extension` | 延期审批结果 | 延期类别标识 |
| `complaint` | 投诉处理结果 | 投诉类别标识 |
| `appeal` | 申诉最终结果 | 申诉类别标识 |
| `credit_exchange` | 学分兑换结果 | 学分类别标识 |
| `rule` | 规则文件更新 | 规则类别标识 |
| `announcement` | 系统公告 | 公告类别标识 |

`category` 是稳定数据字段。V2 前端不提供按上述类别筛选，但可以按类别显示颜色或图标。

### 4.2 固定事件与收件人

| message_type | 触发条件 | 收件人 | biz_type |
|---|---|---|---|
| `task_publish_approved` | 管理员批准教师任务发布申请 | 发布教师 | `college_task` |
| `task_publish_rejected` | 管理员驳回教师任务发布申请 | 发布教师 | `college_task` |
| `task_registration_selected` | 指导老师完成筛选，该报名入选 | 对应报名学生 | `college_task` |
| `task_registration_not_selected` | 指导老师完成筛选，该报名未入选 | 对应报名学生 | `college_task` |
| `task_cancelled` | 已发布任务完成取消事务 | 所有未取消、未删除的有效报名学生 | `college_task` |
| `hour_application_advisor_rejected` | 指导老师驳回课时申请或任务成果 | 需要修改和重提的申请发起人；团队任务为队长 | `hour_application` |
| `hour_application_review_assigned` | 管理员把审核任务分配给审核老师 | 被分配的审核老师 | `hour_application` |
| `hour_application_final_approved` | 管理员最终确认课时 | 个人申请为申请人；团队申请为全部有效成员 | `hour_application` |
| `hour_application_final_rejected` | 管理员最终驳回课时 | 个人申请为申请人；团队申请为全部有效成员 | `hour_application` |
| `extension_approved` | 指导老师或管理员批准延期 | 延期申请人 | `extension_request` |
| `extension_rejected` | 指导老师或管理员驳回延期 | 延期申请人 | `extension_request` |
| `complaint_resolved` | 管理员提交投诉处理结果 | 实名投诉人 | `complaint` |
| `appeal_completed` | 申诉流程形成最终结果 | 申诉人 | `appeal` |
| `credit_exchange_approved` | 管理员最终确认兑换并完成入账 | 分配明细中的全部有效成员，包括分配值为 0 的成员 | `credit_exchange` |
| `credit_exchange_rejected` | 指导老师或管理员驳回兑换 | 负责修改、重提或申诉的申请发起人；团队为队长 | `credit_exchange` |
| `rule_updated` | 管理员发布新的有效规则文件 | 触发时全部正常使用用户 | `rule_file` |
| `system_announcement` | 管理员发布系统公告 | 公告选择范围内的正常使用用户 | 空或公告批次 |

### 4.3 明确不生成消息的动作

- 投诉已受理、申诉已受理。
- 保存草稿、普通提交成功等当前操作页面已经即时反馈的动作。
- 管理员查看详情、下载附件、普通列表查询。
- 没有用户意义的内部中间状态。
- 同一业务状态被重复写入。
- 尚未明确处理人的管理员待办。

### 4.4 管理员待办规则

- 业务已经分配明确处理人时，只通知该处理人。
- 尚未分配处理人时，不群发给全部管理员，由管理员工作台待办列表承接。
- 审核老师分配属于明确处理人场景，使用 `hour_application_review_assigned`。
- 后续业务如果新增管理员指派关系，再为指定管理员增加对应事件，不得默认群发。

## 5. 数据库契约

### 5.1 `notifications` 表

V2 使用单消息表。公告也按收件人展开写入该表，不在本期拆分公告主表和投递表。

| 字段 | 类型建议 | 允许空 | 约束与语义 |
|---|---|---|---|
| `id` | BigInteger | 否 | 主键 |
| `recipient_user_id` | BigInteger | 否 | 外键 `users.id`，消息所有者 |
| `actor_user_id` | BigInteger | 是 | 触发操作用户；系统事件可空 |
| `category` | String(32) | 否 | 第 4.1 节固定枚举 |
| `message_type` | String(64) | 否 | 第 4.2 节固定事件代码 |
| `title` | String(200) | 否 | 列表标题快照 |
| `content` | Text | 否 | 详情正文快照；驳回消息保存完整原因 |
| `biz_type` | String(64) | 是 | 稳定业务类型 |
| `biz_id` | BigInteger | 是 | 原业务主键 |
| `payload` | JSON | 是 | 小型展示扩展，不得复制完整业务对象或附件 |
| `academic_year` | String(16) | 否 | 创建时学年快照，如 `2026-2027` |
| `semester` | String(16) | 否 | 创建时学期快照，取系统配置固定值 |
| `announcement_batch_key` | String(64) | 是 | 同一公告向多个收件人展开时共享的批次键 |
| `announcement_audience` | String(255) | 是 | 公告目标角色的规范化快照；普通业务消息为空 |
| `replaced_by_batch_key` | String(64) | 是 | 旧公告被替换时指向新公告批次 |
| `expires_at` | DateTime | 是 | 公告失效时间；普通业务消息为空 |
| `stopped_at` | DateTime | 是 | 公告停止时间；普通业务消息为空 |
| `withdrawn_at` | DateTime | 是 | 公告紧急撤回时间；普通业务消息为空 |
| `dedupe_key` | String(200) | 否 | 单收件人业务幂等键 |
| `read_at` | DateTime | 是 | 第一次阅读时间；空表示未读 |
| `created_at` | DateTime | 否 | 创建时间，遵循项目统一时间规范 |

不增加 `priority`、`is_read`、`archived_at`、`action_url` 和外部渠道投递字段。

### 5.2 系统学期配置

消息创建必须能获得当前学期快照。V2 开发前需要在 `system_configs` 中冻结并提供以下键值：

| config_key | 示例 | 说明 |
|---|---|---|
| `current_academic_year` | `2026-2027` | 当前学年 |
| `current_semester` | `1` | 当前学期固定枚举 |

配置不存在或格式非法时，业务状态不得在已经提交后因为消息失败而出现半成功。开发实现必须在启动检查或业务操作前发现配置问题，并给出明确运维错误。

### 5.3 约束与索引

```text
UNIQUE(recipient_user_id, dedupe_key)
INDEX(recipient_user_id, academic_year, semester, created_at, id)
INDEX(recipient_user_id, academic_year, semester, read_at, id)
INDEX(announcement_batch_key, recipient_user_id)
INDEX(replaced_by_batch_key)
INDEX(biz_type, biz_id)
```

批量公告插入前应去重用户 ID。外键删除策略应避免物理删除用户导致历史消息失去归属；系统用户删除继续采用现有停用或软删除口径。

### 5.4 幂等键

每次业务事件必须生成稳定 `dedupe_key`，示例：

```text
task-publish:{task_id}:{decision_version}:{decision}
task-registration:{registration_id}:{selection_round}:{decision}
task-cancel:{task_id}:{cancel_version}
hour-application:{application_id}:{review_round}:{stage}:{decision}
extension:{extension_request_id}:{decision_version}:{decision}
complaint:{complaint_id}:result:{result_version}
appeal:{appeal_id}:{round_no}:completed:{decision}
credit-exchange:{exchange_id}:{review_round}:{stage}:{decision}
rule-file:{rule_file_id}:published:{version}
announcement:{announcement_batch_key}
```

重新审核、申诉重开、更正结果和公告替换必须产生新版本或新批次，不能被首次事件的唯一键错误拦截。

## 6. 用户接口契约

所有接口前缀为 `/api/v1`，要求登录，并使用项目统一响应包络：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 6.1 查询消息列表

```http
GET /api/v1/notifications
```

| 参数 | 必填 | 默认值 | 规则 |
|---|---|---|---|
| `page` | 否 | `1` | 大于等于 1 |
| `page_size` | 否 | `20` | 1～100 |
| `status` | 否 | `all` | `all/read/unread` |
| `academic_year` | 否 | 当前学年 | 必须与 `semester` 成对使用 |
| `semester` | 否 | 当前学期 | 必须与 `academic_year` 成对使用 |

V2 不接收前端业务 `category` 筛选参数。固定排序：`created_at DESC, id DESC`。

响应数据：

```json
{
  "items": [
    {
      "id": 135,
      "category": "hour_application",
      "message_type": "hour_application_final_rejected",
      "title": "课时申请终审驳回",
      "content_preview": "请进入详情查看完整原因",
      "biz_type": "hour_application",
      "biz_id": 23,
      "academic_year": "2026-2027",
      "semester": "1",
      "is_read": false,
      "read_at": null,
      "created_at": "2026-08-08T15:30:00+08:00"
    }
  ],
  "page": 1,
  "page_size": 20,
  "total": 1,
  "pages": 1,
  "selected_period": {"academic_year": "2026-2027", "semester": "1"},
  "available_periods": [{"academic_year": "2026-2027", "semester": "1"}]
}
```

列表不返回完整驳回原因和业务附件。

### 6.2 查询未读数量

```http
GET /api/v1/notifications/unread-count
```

可选接收成对的 `academic_year`、`semester`；不传时统计当前学期。

```json
{
  "unread_count": 8,
  "latest_notification_id": 135,
  "academic_year": "2026-2027",
  "semester": "1"
}
```

前端每 60 秒轮询，也允许手动刷新。

### 6.3 查询消息详情

```http
GET /api/v1/notifications/{notification_id}
```

- 只允许消息收件人查询。
- 消息不存在或不属于当前用户统一返回 404，避免枚举他人消息。
- 返回完整 `content`、业务关联和公告状态。
- GET 不自动标记已读。
- 原业务不存在时仍返回消息快照，同时返回 `biz_available=false`。

### 6.4 单条标记已读

```http
POST /api/v1/notifications/{notification_id}/read
```

重复调用返回成功并保留第一次 `read_at`。

### 6.5 批量选择标记已读

```http
POST /api/v1/notifications/read
```

```json
{"ids": [1, 2, 3]}
```

- `ids` 必须是去重后的整数数组，单次最多 100 条。
- 只更新当前用户拥有的 ID。
- 请求中混入他人或不存在的 ID 时，不泄露其归属；响应只返回实际更新数和已是已读数。

### 6.6 全部标记已读

```http
POST /api/v1/notifications/read-all
```

```json
{
  "up_to_id": 135,
  "academic_year": "2026-2027",
  "semester": "1"
}
```

只更新当前用户、指定学期、`id <= up_to_id` 且当前未读的消息。请求执行期间新到达且 ID 更大的消息保持未读。

## 7. 管理员公告接口契约

所有正常管理员均可发布、停止和替换公告。公告紧急撤回必须绑定单独的高权限能力，不能仅凭普通管理员角色开放。

### 7.1 发布公告

```http
POST /api/v1/admin/notifications/announcements
```

```json
{
  "title": "系统维护通知",
  "content": "系统将于今晚维护。",
  "audience_roles": ["student", "advisor", "reviewer", "admin"],
  "expires_at": null
}
```

规则：

- `audience_roles` 允许选择学生、指导老师、审核老师、管理员；传全部角色等价于全部正常用户。
- 角色数组必须去重、按固定顺序规范化，并保存到 `announcement_audience`，保证公告批次查询不依赖前端原始顺序。
- 不支持指定学院、指定用户和预约发布。
- 实际发布时间就是生效时间。
- 未填写 `expires_at` 表示长期有效。
- 对目标用户 ID 去重后，每人创建一条消息，共享 `announcement_batch_key`。

### 7.2 查询公告批次

```http
GET /api/v1/admin/notifications/announcements
```

按批次返回标题、发布者、目标角色、收件人数、发布时间、失效时间、停止时间、撤回时间和替换批次。

### 7.3 停止公告

```http
POST /api/v1/admin/notifications/announcements/{batch_key}/stop
```

停止后：

- 不再作为当前公告展示；
- 已收到用户仍能查看历史消息；
- 不物理删除消息。

### 7.4 替换公告

```http
POST /api/v1/admin/notifications/announcements/{batch_key}/replace
```

请求体与发布公告相同。事务内停止旧批次、创建新批次，并把旧批次各行的 `replaced_by_batch_key` 指向新批次；两批记录均保留。

### 7.5 紧急撤回公告

```http
POST /api/v1/admin/notifications/announcements/{batch_key}/withdraw
```

- 仅具备 `announcement_emergency_withdraw` 能力的高权限管理员可调用。
- 用于违法、泄密或明显误发，不作为普通编辑功能。
- 撤回后普通收件人不再看到正文，详情返回统一撤回提示；原内容按审计和合规策略受控保留。
- 当前系统尚无该权限能力，必须在开发前完成权限映射评审。

## 8. 业务跳转与附件

- 后端只返回 `biz_type`、`biz_id` 和 `biz_available`，不保存前端 URL。
- 前端按当前角色维护业务详情页面映射。
- `biz_available=false` 时禁用跳转并提示“该业务不存在”。
- 消息不复制附件；附件继续通过原业务附件接口鉴权。
- 原附件删除或用户无权访问时，不得因为持有消息 ID 而获得附件。
- 驳回原因列表只显示摘要提示，消息详情显示完整原因。

## 9. 事务、一致性和并发

### 9.1 同事务原则

业务状态写入和对应站内消息写入必须在同一个数据库事务中提交：

```text
校验权限与状态
→ 写业务状态/结果
→ 计算收件人
→ 创建消息
→ 写操作日志
→ 统一 commit
```

任一步失败，整笔业务操作回滚。消息服务不得自行 `commit()`。

### 9.2 幂等原则

- 数据库唯一约束是最终防线。
- 服务层先按收件人和 `dedupe_key` 查重。
- 重复业务请求不得生成重复消息。
- 批量业务中每个业务对象保持原接口约定的事务边界；单笔内部业务和消息不可分离。

### 9.3 并发规则

- 两个请求同时标记已读，只允许第一次写入时间，最终状态为已读。
- 标记已读和新消息并发时，`up_to_id` 保护新消息。
- 同一业务事件并发触发时，唯一键阻止重复消息。
- 公告发布前固化收件用户集合；发布过程中账号状态变化不回写已经创建的收件记录。
- 公告停止、替换和撤回必须校验当前批次状态，非法重复状态转换返回 409。

## 10. 权限与安全

- 所有用户接口必须登录。
- 收件人只能读取和修改自己的阅读状态。
- 非本人消息与不存在消息统一返回 404。
- 客户端不得提交或覆盖 `recipient_user_id`、`actor_user_id`、`read_at`。
- 标题、正文和公告内容必须限制长度，并按纯文本或受控富文本策略防止 XSS。
- `payload` 不保存密码、联系方式、身份证件、内部管理员意见等敏感信息。
- 投诉消息不显示处理管理员姓名。
- 公告发布、停止、替换、撤回和运维删除必须写操作日志。
- 停用账号不能通过历史会话继续调用消息接口，应复用现有登录态失效策略。

## 11. 异常响应

| 场景 | HTTP 状态 | 规则 |
|---|---:|---|
| 未登录 | 401 | 统一认证错误 |
| 普通用户调用公告管理接口 | 403 | 不具备管理员权限 |
| 消息不存在或非本人 | 404 | 不泄露对象归属 |
| 业务关联不存在 | 200 | 消息仍返回，`biz_available=false` |
| 分页、状态、学期参数非法 | 400 | 明确字段错误 |
| 状态重复或非法公告转换 | 409 | 返回当前状态 |
| 重复标记已读 | 200 | 幂等成功 |
| 重复业务事件 | 原业务语义 | 不重复创建消息 |
| 消息写入失败 | 原业务请求失败 | 同事务回滚 |

## 12. 开发顺序

1. 完成 V2 前安全修复的后端测试和前端回归。
2. 冻结当前学年、学期配置值与高权限公告撤回能力。
3. 增加模型、迁移、枚举和序列化契约。
4. 实现只负责 `flush`、不自行提交的消息领域服务。
5. 实现用户收件箱与阅读接口。
6. 实现公告发布、查询、停止、替换与受控撤回。
7. 按事件目录逐个接入现有业务服务。
8. 对尚不存在的投诉完成、任务取消等业务能力，在其业务模块完成后接入对应触发点。
9. 完成单元、接口、权限、事务、并发和回归测试。
10. 向前端交付最终接口契约、枚举、示例、测试账号和联调数据后开始联调。

## 13. 验收标准

- 第 4.2 节每个已具备业务触发点的事件均能生成正确消息。
- 收件人、类别、业务关联、学期快照和正文符合事件目录。
- 同一事件重试不产生重复消息。
- 业务事务失败不残留消息，消息失败不留下已提交业务状态。
- 用户不能查看或标记他人消息。
- 单条、批量和全部已读均满足幂等和 `up_to_id` 边界。
- 当前学期默认展示，历史学期可切换，长期保留不等于物理删除。
- 公告受众按账号和角色状态正确展开，停止、替换、到期、撤回语义符合规格。
- 原业务或附件不存在时不越权、不报 500，并返回约定提示。
- 未读数量接口可支持 60 秒轮询，不依赖 Redis 或 WebSocket。
- 全部原有 V1 后端自动化测试继续通过。
