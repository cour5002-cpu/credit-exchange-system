# V1 复盘与 V2 架构治理方案

> 文档状态：V1 前端最终检查阶段的复盘稿  
> 编制日期：2026-08-03  
> 适用范围：当前课时兑换学分系统后端、前后端联调及后续 V2 开发  
> 本文性质：分析与改造建议，不代表已经完成代码重构

## 1. 文档目的

V1 的主要业务需求已经完成，目前仅剩前端检查。本次复盘不以追究某一方责任为目的，而是解决以下问题：

1. 汇总 V1 开发和联调阶段产生返工的主要类型、根因及影响。
2. 明确 V2 及后续版本在需求、接口、测试和沟通方面必须增加的检查事项。
3. 评估当前代码结构是否仍然清晰、统一和易于扩展。
4. 拆解已有结构问题，给出不改变现有业务行为的渐进式治理方案。
5. 明确结构调整后需要与前端重新确认和回归测试的范围。
6. 说明目标架构、拆分依据、潜在风险以及风险控制方法。

本文依据当前仓库代码、需求文档、接口文档、状态流转文档、联调记录和自动化测试情况编写。截至本文编制时，现有自动化测试共 25 项，执行结果全部通过。但“测试通过”仅证明已覆盖场景当前可运行，不等于所有边界、并发和兼容场景均已覆盖。

## 2. V1 返工问题总结

### 2.1 总体结论

V1 后期出现的许多问题并不是简单的语法错误或代码写错，而是前后端对同一需求的业务语义、状态含义、时间边界和页面行为理解不一致。

前期已经向前端提供数据库字段、主线流程和接口文档，这些资料解决了“数据存在哪里”“主要流程怎么走”“调用什么接口”等问题，但还没有完全覆盖以下内容：

- 某一状态具体属于哪个业务对象；
- 某一状态在什么时刻产生；
- 页面在该状态下展示什么、允许什么操作；
- 正常路径之外的驳回、过期、重复操作和越权如何处理；
- 请求和响应中空值、时间、金额、附件及分页如何表达；
- 前端展示逻辑与后端最终裁决之间如何划分职责；
- 同一业务动作涉及多个数据对象时，它们的状态如何同步变化。

因此，V1 后期返工的本质是“静态资料较完整，但可执行的业务契约不够完整”。

### 2.2 已出现或容易出现的返工类型

#### 2.2.1 状态语义不一致

典型情况包括：

- 延期申请记录的状态和课时申请主记录的状态被混为一套状态理解。
- `submitted`、`pending_review` 等通用词在不同业务对象中含义不同。
- 任务成果提交后应该进入课时申请的哪一个环节，前后端理解不一致。
- 申诉的总状态和申诉重新打开后的具体处理阶段没有被明确区分。
- 页面状态、按钮状态和数据库状态之间缺少明确映射。

根因是接口文档列出了状态值，但缺少“状态所属对象 + 进入条件 + 可执行动作 + 下一状态 + 页面表现”的完整状态契约。

#### 2.2.2 时间和截止边界不一致

典型情况包括：

- 前端使用浏览器本地时间判断能否报名，后端使用服务器时间判断。
- `registration_deadline` 到达时，到底是 `>` 截止还是 `>=` 截止没有提前冻结。
- 无时区时间、UTC 时间和上海时间在前端、API、Python 与 MySQL 之间转换口径不一致。
- 倒计时用于展示还是用于业务裁决没有明确分工。

正确原则应是：前端时间只用于展示，能否操作以服务端响应为准；输入输出时间格式和时区必须形成统一契约。

#### 2.2.3 新建、修改、重提和版本保留语义不一致

典型情况包括：

- 成果被驳回后，前端可能按“重新提交”理解为创建一条新主记录；后端则可能要求修改原记录。
- 当前版本附件与历史版本附件的返回范围不明确。
- 草稿保存、正式提交和驳回重提是否使用同一接口没有完全冻结。

这类问题会直接影响主键、列表数量、历史追踪和附件展示，必须在接口设计阶段明确“资源身份是否改变”。

#### 2.2.4 返回数据和页面预期不一致

典型情况包括：

- 没有当前生效兑换规则时，成员是否仍应返回。
- 空数据使用 `null`、空数组、空字符串还是不返回字段。
- 列表接口和详情接口中的同名字段含义或结构不同。
- 页面需要 `can_submit`、`can_review` 等操作标记，但原接口只返回数据库状态。
- 前端期望驼峰字段，后端实际采用下划线字段。

数据库字段不等同于前端视图模型。前端真正依赖的是稳定的 API 响应契约，而不是数据库设计本身。

#### 2.2.5 权限与角色边界不一致

典型情况包括：

- “教师”并不等于同时拥有指导老师和审核老师权限。
- 同一个教师角色只能查看自己负责的数据，不能仅靠前端隐藏按钮。
- 学生、队长、任务成员对成果详情和附件的可见范围不同。
- 管理员的查看权限、审核权限、关闭权限需要分别说明。

权限必须由后端强制校验，前端按钮控制只用于改善体验，不能作为安全边界。

#### 2.2.6 正常流程明确，但异常和边界流程不足

V1 前期主要围绕主线流程展开，以下场景往往到联调阶段才被发现：

- 重复点击提交或审批；
- 数据已被其他人处理后再次操作；
- 报名截止前提前筛选；
- 截止后仍停留在报名状态；
- 附件上传后尚未绑定、绑定后删除、提交后作废；
- 当前规则失效或被替换；
- 申诉过程中原业务又发生状态变化；
- 某条主数据存在，但当前用户无权查看。

### 2.3 返工频繁发生的流程原因

除具体需求外，开发协作方式也放大了返工概率：

1. **联调单位偏向单个接口，而不是完整业务场景。** 单个接口返回 200 不代表页面闭环成立。
2. **文档没有全部转化为自动检查。** 文档、后端和前端可能分别正确，但彼此不一致。
3. **页面行为确认较晚。** 如果前端页面完成后才验证状态与按钮映射，差异会集中暴露。
4. **修改影响范围没有形成固定清单。** 改状态后可能只改代码，没有同步检查接口文档、页面文档、测试和初始化数据。
5. **Git 提交粒度偏大。** 当前历史提交数量较少且覆盖范围较大，不利于定位某一业务决策何时改变。

### 2.4 频繁返工的影响

- 同一问题需要同时修改数据库、模型、服务、接口、文档、测试和前端页面。
- 局部修复可能破坏另一个角色或另一条流程。
- 状态值和兼容逻辑不断累积，增加后续理解成本。
- 开发人员逐渐无法确定哪些代码是正式实现、哪些是历史兼容。
- 测试和联调时间超过功能本身的实现时间。
- 后续版本的修改风险和评估成本持续上升。
- 如果提交粒度过大，出现问题时难以精确回退。

### 2.5 对返工的合理认识

V1 联调出现返工并不意味着项目失败。多角色、多阶段审批系统只有在真实页面和完整数据流连通后，许多隐含规则才会暴露。需要改进的不是“完全杜绝修改”，而是：

- 尽可能让歧义在编码前暴露；
- 让契约差异在自动测试中暴露；
- 让一次修改只影响可预期的业务模块；
- 让修改原因、影响范围和回归结果可以追踪。

## 3. V2 及后续版本需要增加的检查事项

### 3.1 需求进入开发前的检查

每一项需求至少回答以下问题后才能进入开发：

- 需求服务于哪个角色？
- 操作的业务对象是什么？
- 前置状态是什么？
- 操作成功后哪些对象发生变化？
- 失败、驳回、撤回、关闭和过期如何处理？
- 是否允许重复操作？
- 是否存在截止时间和边界值？
- 是否涉及附件、金额、课时、学分或个人信息？
- 哪些角色可查看，哪些角色可修改？
- 是否需要操作日志、历史版本或规则快照？
- 是否影响现有 V1 接口和数据？
- 验收时如何证明需求已经完成？

建议每个需求使用“角色—动作—对象—规则—结果”的句式描述。例如：

> 已报名且被选中的学生中，指导老师必须指定一人为队长；指定成功后任务进入进行中状态，只有该队长能够提交成果。

### 3.2 状态机检查

每个具有生命周期的业务对象必须独立维护状态表，至少包含：

| 检查项 | 说明 |
|---|---|
| 状态所属对象 | 避免多个表共用一个模糊状态词 |
| 进入条件 | 哪个动作或定时条件产生该状态 |
| 操作角色 | 哪个角色能够执行动作 |
| 前置状态 | 只允许从哪些状态进入 |
| 下一状态 | 成功、驳回、关闭分别去哪里 |
| 是否终态 | 是否允许继续修改 |
| 页面表现 | 展示文案、按钮和提示 |
| 并发处理 | 数据已被处理时如何响应 |
| 审计要求 | 是否记录操作人、意见和前后状态 |

状态名称相同但业务对象不同的，文档中必须写全称，例如“成果提交状态 submitted”，不能只写“submitted”。

### 3.3 API 契约检查

每个接口必须至少确认：

- HTTP 方法和路径；
- 认证方式和允许角色；
- Path、Query、Body、Cookie 各自参数；
- 字段类型、是否必填、默认值和取值范围；
- 完整成功响应示例；
- 完整失败响应示例；
- 空值和空集合表达；
- 时间格式和时区；
- 分页结构和排序规则；
- 幂等性或重复提交行为；
- 业务错误码与 HTTP 状态码；
- 涉及的数据状态变化；
- 兼容性要求和废弃计划。

建议引入 OpenAPI，将其作为请求响应的机器可读契约，并通过 schema 校验或契约测试防止实现偏离文档。

### 3.4 页面行为检查

每个页面需要建立“页面—接口—状态—按钮”矩阵：

| 页面状态 | 展示内容 | 可用按钮 | 调用接口 | 成功后页面变化 | 失败提示 |
|---|---|---|---|---|---|
| 加载中 | 骨架/加载提示 | 禁用 | GET 详情 | 展示详情 | 支持重试 |
| 可操作 | 当前数据 | 按角色显示 | POST/PATCH | 刷新详情和列表 | 显示业务原因 |
| 已处理 | 最新状态 | 禁止重复操作 | GET 详情 | 保留结果 | 提示已被处理 |
| 无权限 | 不展示敏感数据 | 无 | GET 详情 | 返回上一页 | 统一 403 提示 |
| 数据不存在 | 空态 | 无 | GET 详情 | 返回列表 | 统一 404 提示 |

### 3.5 时间检查

- API 输入推荐使用带偏移量的 ISO 8601 时间，例如 `2026-08-10T18:00:00+08:00`。
- API 输出必须带明确偏移量。
- 数据库存储方式和应用层转换方式必须固定。
- 所有截止判定统一使用后端业务时间。
- 前端倒计时只负责展示，操作成功与否以后端返回为准。
- 明确截止边界是 `server_time >= deadline` 还是其他规则。
- 测试必须覆盖截止前、恰好截止和截止后三个点。

### 3.6 数据一致性与事务检查

对于一次动作修改多个对象的情况，例如“成果审核通过并生成课时申请”或“兑换通过并扣减课时”，必须确认：

- 是否在同一事务中完成；
- 中途失败是否全部回滚；
- 是否可能重复生成记录；
- 是否需要数据库唯一约束；
- 是否记录原规则快照和原状态；
- 是否存在并发审批或重复点击风险；
- 是否需要行锁、乐观锁或幂等键。

### 3.7 权限与安全检查

- 后端按角色和数据归属双重校验。
- 列表权限和详情权限保持一致。
- 附件下载权限与所属业务对象权限保持一致。
- 匿名投诉等功能不得意外暴露提交者身份。
- 导入导出必须校验角色、文件类型、文件大小和字段内容。
- 生产环境密钥、默认账号和调试配置不得沿用开发值。
- 日志中不得记录密码、Cookie 和不必要的敏感数据。

### 3.8 测试检查

V2 每个业务模块至少包括：

1. 正常主线测试；
2. 每个角色的权限测试；
3. 非法状态转换测试；
4. 重复提交测试；
5. 边界值测试；
6. 空数据和无当前规则测试；
7. 附件权限测试；
8. 时间与时区测试；
9. 数据库约束和事务回滚测试；
10. 与现有 V1 流程的回归测试。

除测试数量外，应增加覆盖率报告，但不能单独以覆盖率百分比判断业务质量。

### 3.9 发布前检查

- 数据库迁移在空数据库和现有 V1 数据库上均可执行。
- 初始化数据与正式枚举、角色、配置一致。
- OpenAPI、接口文档、状态文档和代码一致。
- 前端生产配置不包含临时隧道地址或测试账号。
- 核心业务自动化测试全部通过。
- 完成一次多角色端到端人工验收。
- 准备备份、回退和迁移失败处理方案。

## 4. V2 及后续版本需要增加的沟通事项

### 4.1 需求评审时前后端共同确认

- 页面原型和业务状态是否一一对应；
- 前端展示状态是否直接使用后端状态，还是映射为页面状态；
- 页面需要哪些派生字段和操作标记；
- 草稿、提交、撤回、驳回、重提是否改变资源 ID；
- 列表进入详情后，数据被其他用户修改时如何处理；
- 错误提示由后端提供到什么粒度；
- 是否允许前端进行乐观更新；
- 文件上传和正式提交是一个动作还是两个动作。

### 4.2 接口开发前共同确认

- 使用真实完整 JSON 示例确认字段，而不是只看字段表。
- 明确同名字段在列表和详情中的结构是否相同。
- 确认 `null`、`[]`、`false` 和字段缺失的区别。
- 确认数值是 JSON number 还是字符串。
- 确认时间格式、时区和截止边界。
- 确认分页、筛选和排序参数。
- 确认 400、401、403、404、409、422、500 的使用口径。

### 4.3 联调前共同确认

- 前端使用统一请求实例、统一 `/api/v1` 基础路径和 Cookie 配置。
- 后端提供可重复初始化的测试数据。
- 每个角色准备独立测试账号。
- 按业务闭环确定联调顺序，不按文件或接口编号机械联调。
- 双方明确问题记录格式：场景、账号、请求、响应、预期、实际和复现步骤。

### 4.4 需求变化时共同确认

任何涉及以下内容的变化，应视为契约变更，而不是普通 Bug 修复：

- 字段新增、删除、改名或类型改变；
- 状态值或状态流转改变；
- 权限和数据可见范围改变；
- 时间和截止规则改变；
- 资源新建、覆盖或版本保留方式改变；
- HTTP 状态码和错误码改变；
- 列表、详情或附件结构改变。

契约变更必须同步更新：需求/决策记录、OpenAPI 或接口文档、后端实现、后端测试、前端类型定义、页面逻辑和联调用例。

### 4.5 推荐的联调场景表

以后以场景为联调单位，每一行至少包含：

```text
场景编号 | 操作角色 | 前置数据 | 页面动作 | API 请求 | 预期响应
        | 数据状态变化 | 页面变化 | 异常分支 | 前端结果 | 后端结果
```

例如任务报名闭环应一次性验证：

```text
发布任务 → 截止前学生报名 → 截止前禁止筛选 → 截止后报名被拒绝
→ 任务进入待筛选 → 指导老师筛选 → 指定队长 → 队长提交成果
```

## 5. 当前代码结构概览与问题汇总

### 5.1 当前结构的积极部分

当前项目并非完全无结构，已经具备以下基础：

- 使用 Flask 应用工厂创建应用。
- 扩展初始化、模型、服务、路由、工具、命令、迁移和测试已经分目录管理。
- 主要业务逻辑已从页面路由中部分抽取到服务层。
- 具备角色权限工具、统一时间工具、分页工具和编号生成工具。
- 通过 SQLAlchemy 模型表达主要数据关系。
- 使用迁移脚本管理数据库变化。
- 主要业务闭环已有自动化 API 测试。
- 成果版本、规则快照、账户流水和操作日志等设计有利于审计追踪。

因此，当前代码可以继续支撑 V1；问题主要在于模块规模、边界和一致性，不需要推倒重写。

### 5.2 当前问题清单

#### P1：API 聚合文件过大

`app/modules/api/routes.py` 当前约 2536 行，包含：

- 认证和当前用户；
- 任务类型和教师选项；
- 导入导出；
- 附件上传、下载、删除和操作记录；
- 规则文件和兑换规则；
- 课时申请与延期；
- 指导老师、审核老师和管理员审核；
- 学分兑换；
- 申诉；
- 学院任务、报名、成员和成果；
- 投诉；
- 操作记录；
- 响应包装、分页处理和大量序列化函数。

问题不在于单纯行数，而在于一个文件同时承担了路由注册、输入提取、错误处理、响应 DTO 组装、文件处理和部分业务判断。任一模块修改都可能需要在同一个文件中定位多个位置，冲突和遗漏概率随功能增加而上升。

#### P2：服务以开发周命名，不能表达长期业务边界

当前主要服务包括：

- `week3_hour_application_service.py`，约 862 行；
- `week4_credit_exchange_service.py`，约 685 行；
- `week5_appeal_task_service.py`，约 897 行。

“week3/week4/week5”说明了开发时间，不能说明代码职责。其中 `week5_appeal_task_service.py` 同时包含申诉、任务、成果和投诉，已经形成多个业务域耦合。

#### P3：新旧服务并存

项目中同时存在：

- `hour_application_service.py` 与 `week3_hour_application_service.py`；
- `credit_exchange_service.py` 与 `week4_credit_exchange_service.py`；
- 传统服务端页面路由与新增 `/api/v1` API 路由。

这并不一定立即产生运行错误，但会使开发人员难以判断哪个入口是正式实现、哪个仅用于旧页面兼容。后续若两套服务分别修复同一规则，很容易产生行为差异。

#### P4：服务之间存在横向依赖

兑换服务从课时申请服务导入 `BusinessError`、`current_student`、`current_teacher`；申诉任务服务又导入课时申请和兑换服务中的多个审核方法。

这种依赖在 V1 可以工作，但随着模块增长会产生：

- 循环依赖风险；
- 一个模块重构影响另一个模块；
- 公共身份解析和异常类归属不清；
- 事务边界难以统一。

#### P5：状态字符串和转换规则分散

状态值分散在模型标签、服务常量、查询条件、路由操作标记和文档中。当前模型还保留服务端旧页面的 legacy 状态。

风险包括：

- 改名时漏改某个查询或按钮标记；
- 文档允许的转换和代码实际允许的转换不一致；
- 不同业务对象复用相同字符串导致误解；
- 非法状态可能在缺少统一入口时被直接赋值。

#### P6：响应 DTO/序列化层缺失

大量 `_xxx_payload`、`_xxx_summary` 和 `_xxx_detail` 函数位于 API 路由文件中。数据库模型、业务服务和前端响应之间缺少独立的 schema/serializer 层。

这使得：

- 列表和详情字段容易不一致；
- 时间、Decimal、空值需要重复手工转换；
- 响应变更会直接修改路由大文件；
- 难以自动生成 OpenAPI 和做响应校验。

#### P7：请求校验和辅助函数重复

多个服务分别实现 `_required_str`、`_required_int`、`_normalize_id_list`、`_parse_datetime` 等函数。重复实现可能在错误消息、空值处理和边界行为上逐渐不同。

需要注意：并非所有校验都应无条件抽成一个巨大工具类。通用格式校验可以复用，业务规则仍应留在所属业务域。

#### P8：事务提交分散在服务方法中

许多服务方法内部直接调用 `db.session.commit()`。单一用例当前可控，但跨模块业务编排时，上层无法方便地把多个动作纳入同一事务。

例如申诉重新打开后可能复用原审核服务；若被调用的方法内部先提交，后续申诉状态更新失败，就可能出现部分成功。

#### P9：查询、状态推进和副作用混合

部分列表或详情查询可能顺便推进过期任务状态并提交数据库。这种“读取触发写入”会让 GET 请求带有副作用，影响缓存、测试和问题定位。

V1 可保留现有行为以保证截止自动推进，但 V2 应明确由定时任务、写操作前校验或专门的状态同步机制承担。

#### P10：模型同时承载新旧字段和兼容语义

以课时申请模型为例，既包含当前 V1 流程字段，也保留早期服务端页面字段和 legacy 状态。短期兼容合理，长期会导致：

- 同一概念存在多个字段；
- 新代码不确定应读取哪个字段；
- 数据迁移和清理越来越困难。

#### P11：错误处理未完全统一

当前已有 `BusinessError`、API 的 `ok/fail` 包装和 Flask 全局 403/404/413 处理，这是良好基础；但业务错误处理仍集中在 API 路由，其他服务或蓝图可能采用不同表达方式。

#### P12：测试基础已建立，但缺少更细的结构保障

当前 25 项测试覆盖主要流程，是现有重构的重要安全网。但仍建议增加：

- 每个状态转换的参数化测试；
- 响应 schema/契约测试；
- 重复提交和并发审批测试；
- 事务中途失败回滚测试；
- 数据迁移测试；
- 新旧入口行为是否需要保持一致的兼容测试；
- 测试覆盖率报告。

## 6. 代码结构拆解依据与合理性

### 6.1 拆分不应只按文件行数

行数只是风险信号，真正拆分依据应是：

1. **业务对象是否具有独立生命周期。** 课时申请、兑换申请、申诉、学院任务均有自己的状态机。
2. **业务规则是否具有高内聚性。** 报名、筛选、队长、成果都围绕学院任务，但投诉不属于任务生命周期。
3. **修改是否经常一起发生。** 同一接口的路由、schema、service 和测试应能在同一模块附近找到。
4. **是否能够独立测试。** 拆分后的模块应允许单独验证正常和异常流程。
5. **事务边界是否清晰。** 一个用例修改哪些聚合和记录，应由应用服务统一控制。
6. **对外契约是否可保持不变。** 内部拆分不应强迫前端立即修改 URL 或字段。

### 6.2 为什么按业务域拆分

按角色拆分容易让同一个业务流程分散到学生、教师和管理员三个目录；按开发周拆分又不能表达长期职责。按业务域拆分能够把同一对象的状态、规则和用例集中起来。

例如“课时申请”域内部可以包含：

- 学生创建和提交；
- 指导老师确认；
- 延期和补交；
- 管理员分配；
- 审核老师复核；
- 管理员终审；
- 课时入账。

不同角色仍通过权限和用例入口区分，但共享同一套状态机和领域规则。

### 6.3 为什么采用渐进式改造

V1 已经完成，前端仍在最终检查。此时大规模改 URL、表结构和业务规则会扩大回归范围。因此合理顺序是：

1. 先建立完整测试基线；
2. 保持 `/api/v1` URL、请求和响应不变；
3. 只移动和拆分内部代码；
4. 每拆一个业务域立即执行自动化与前端回归；
5. 内部稳定后再讨论 V2 契约变更。

这种方法将“结构重构”和“需求新增”分开，问题出现时更容易判断是重构回归还是新需求错误。

### 6.4 不建议的拆分方式

- 不建议只把一个 2500 行文件机械切成多个同样混乱的文件。
- 不建议建立一个包含所有逻辑的 `common.py` 或 `utils.py`。
- 不建议在没有测试保护时一次性重写所有服务。
- 不建议重构同时修改状态名、URL 和数据库字段。
- 不建议为了形式引入过多抽象层，使简单查询也要跨越大量文件。

## 7. 建议的分阶段修改方案

> 以下均为后续建议，本次不实施。

### 阶段 0：冻结 V1 基线

目标：获得可以比较的稳定基线。

- 完成前端最终检查并记录遗留问题。
- 标记 V1 版本或建立可回退提交。
- 固定当前数据库迁移版本。
- 保存 25 项测试的通过结果。
- 补充关键接口的真实请求响应样本。
- 清理或归档临时测试结果文件，但不得误删业务资料。
- 后续每次重构只处理一个业务域并单独提交。

### 阶段 1：抽取跨域基础能力

建议新增或整理：

```text
app/core/
├── errors.py          # BusinessError 及统一错误定义
├── responses.py       # API 成功/失败响应格式
├── identity.py        # 当前学生、当前教师身份解析
├── validation.py      # 通用输入格式校验
├── time.py            # 统一业务时间与 API 时间格式
└── pagination.py      # 统一分页结构
```

合理性：这些能力被多个业务域共同使用，目前却依附于课时申请服务或 API 大文件。先抽取它们可以降低后续域拆分时的横向依赖。

注意事项：业务状态校验、具体角色业务规则不能全部放入 `validation.py`。

### 阶段 2：拆分 API 路由与 schema

在保持 URL 不变的前提下，建议使用一个 `/api/v1` 总蓝图注册业务子蓝图：

```text
app/api/
├── __init__.py
├── auth.py
├── system.py
├── attachments.py
├── imports.py
├── task_types.py
├── hour_applications.py
├── credit_exchanges.py
├── appeals.py
├── college_tasks.py
├── complaints.py
└── operation_logs.py

app/schemas/
├── common.py
├── hour_application.py
├── credit_exchange.py
├── appeal.py
├── college_task.py
└── attachment.py
```

每个路由只负责：

1. 获取请求参数；
2. 调用应用服务；
3. 使用 schema/serializer 输出响应。

文件上传下载可以保留少量 Flask 相关逻辑，但业务归属和权限判断应委托给服务。

### 阶段 3：按业务域拆分服务

建议目标结构：

```text
app/domains/
├── hour_application/
│   ├── statuses.py
│   ├── policies.py
│   ├── commands.py
│   ├── queries.py
│   ├── serializers.py
│   └── repository.py        # 可选，只有查询明显复杂时再引入
├── credit_exchange/
│   ├── statuses.py
│   ├── policies.py
│   ├── commands.py
│   ├── queries.py
│   └── serializers.py
├── appeal/
├── college_task/
├── attachment/
├── complaint/
└── audit/
```

对于当前项目规模，不必一开始实现完整 DDD。目录名称也可以继续使用 `services/<domain>/`。关键是达到以下结果：

- 写操作和读操作职责可区分；
- 状态转换集中；
- 路由不直接拼装复杂业务数据；
- 申诉通过明确的应用服务编排原业务，而不是随意跨服务调用内部方法；
- 投诉从任务/申诉混合服务中独立出来。

### 阶段 4：集中状态和转换策略

每个业务域建立独立状态枚举或常量及合法转换表。例如：

```text
HourApplicationStatus
ExtensionRequestStatus
CreditExchangeStatus
AppealStatus
AppealReopenStage
CollegeTaskStatus
TaskRegistrationStatus
TaskResultStatus
```

状态转换必须通过有语义的方法完成，例如：

```text
submit_application()
approve_by_advisor()
assign_reviewer()
approve_by_reviewer()
final_approve()
```

而不是在多个位置直接写 `application.status = "..."`。

短期可继续在数据库中保存字符串，以避免高风险迁移；Python 层先使用枚举约束。

### 阶段 5：调整事务边界

建议由一个用例级应用服务控制一次业务动作的提交：

```text
路由
  → 应用服务开始用例
    → 查询并校验对象
    → 执行领域动作
    → 写操作日志/流水/版本
    → 统一 commit
  → 返回 DTO
```

被复用的内部领域函数不应自行提交事务。这样申诉重审、任务成果转课时申请、兑换终审等跨对象动作可以保证原子性。

### 阶段 6：处理旧入口和兼容代码

先统计服务端页面是否仍在使用旧 service 和 legacy 字段，然后选择：

- 仍需使用：改为调用新的应用服务，并增加兼容测试；
- 已不使用：标记 deprecated，观察一个版本后移除；
- 仅测试数据使用：修改初始化数据后移除；
- 历史数据库仍有旧状态：先编写数据迁移和校验脚本，再删除兼容逻辑。

不能仅凭文件名称判断旧代码无用，也不能直接删除模型中的 legacy 状态。

### 阶段 7：引入契约和质量门禁

- 建立 OpenAPI 文档。
- 对请求和响应进行 schema 校验。
- 后端测试校验完整响应结构。
- 前端根据 OpenAPI 生成或维护 TypeScript 类型。
- CI 中执行迁移检查、自动化测试和可选的静态检查。
- 对新增状态要求同时提交状态表、测试和页面映射。

## 8. 建议修改后的整体架构分析

### 8.1 总体调用关系

```text
浏览器前端
    ↓ HTTP / Cookie
API 路由层
    ↓ 请求解析、认证入口
Schema / DTO 层
    ↓ 类型与结构校验
应用服务层
    ↓ 用例编排、权限、事务边界
领域规则层
    ↓ 状态转换、业务策略
查询/持久化层
    ↓ SQLAlchemy
MySQL

横向基础能力：时间、错误、分页、身份、附件、审计、日志
```

### 8.2 API 路由层

职责：

- 注册 URL 和 HTTP 方法；
- 处理 Flask request、Cookie 和文件流；
- 调用 schema 校验输入；
- 调用一个明确的应用用例；
- 返回统一响应。

不负责：

- 直接决定复杂状态流转；
- 大量拼装详情响应；
- 跨多个模型完成业务事务；
- 重复实现权限规则。

收益：路由变薄，接口查找和冲突处理更容易。

### 8.3 Schema / DTO 层

职责：

- 定义请求和响应字段；
- 统一 Decimal、日期时间、空值和分页序列化；
- 为 OpenAPI 和前端类型提供来源；
- 区分列表摘要、详情和操作结果。

收益：前端契约不再隐藏在路由函数内部，列表与详情的一致性更容易测试。

### 8.4 应用服务层

职责：

- 表达“提交课时申请”“管理员终审兑换”等完整用例；
- 组织权限检查、领域动作、日志和事务；
- 协调多个业务域；
- 决定何时提交或回滚。

收益：跨对象操作的原子性和可测试性更强。

### 8.5 领域规则层

职责：

- 合法状态转换；
- 角色和业务对象之间的操作规则；
- 课时、学分、延期天数和规则有效期计算；
- 重提、申诉、过期等核心业务约束。

收益：业务规则集中，减少状态字符串和判断条件散落。

### 8.6 查询与持久化层

职责：

- 复杂列表筛选、详情聚合和分页；
- 数据保存和必要的锁策略；
- 隔离 ORM 查询细节。

注意：当前项目不必为每个简单模型强制创建 Repository。只有查询复杂、需要独立测试或未来可能替换数据来源时才引入，以免过度设计。

### 8.7 横向基础能力

#### 时间

统一业务时区、解析、输出和截止判定。

#### 身份与权限

区分登录身份、角色能力和数据归属，避免其他域从课时申请服务导入身份函数。

#### 附件

统一上传、绑定、当前版本、下载权限、软删除和操作记录规则。

#### 审计

统一记录操作人、业务类型、业务 ID、动作、前状态、后状态和时间。

#### 错误

统一业务异常、错误码、HTTP 状态和前端可展示消息。

### 8.8 测试架构

建议形成三层测试：

1. **领域规则单元测试**：快速覆盖每种合法和非法状态转换。
2. **应用服务集成测试**：连接测试数据库验证事务、约束、流水和日志。
3. **API 契约与端到端测试**：验证角色、请求响应结构及完整闭环。

现有 25 项测试可作为第三层和部分第二层的起点，不应在重构时丢弃。

### 8.9 改造后的预期效果

- 一个需求变化更容易定位到所属业务域。
- API URL 和响应契约可以独立于内部实现保持稳定。
- 状态转换和权限规则有唯一或明确来源。
- 跨对象操作可以统一提交和回滚。
- 前端能够从 schema/OpenAPI 获得更可靠的类型和示例。
- V2 新增流程时不必继续向三个大文件追加代码。
- 旧页面兼容逻辑可以有计划地退出，而不是长期混杂。

## 9. 结构修改后必须和前端重新沟通与测试的内容

即使目标是“只重构、不改变外部行为”，仍必须回归以下内容，因为路由拆分、schema 抽取和事务调整都可能产生无意的契约变化。

### 9.1 全局契约回归

- `/api/v1` 基础路径是否保持不变；
- Session Cookie 登录、退出和 `/me` 是否保持不变；
- 401/403/404/409/413/500 的响应结构是否保持不变；
- `code/message/data` 包装是否保持不变；
- CORS、代理和 `withCredentials` 是否保持不变；
- 分页字段、默认页大小和排序是否保持不变；
- 时间输出是否仍带 `+08:00`；
- Decimal、布尔值、`null` 和空数组格式是否保持不变。

### 9.2 课时申请回归

- 有成果和无成果申请的草稿、提交、列表和详情；
- 主指导老师与查看导师的权限差异；
- 补交成果和再次确认；
- 普通延期、特殊延期、驳回及管理员关闭；
- 管理员分配、审核老师审核、管理员终审；
- 驳回后的重新提交或申诉入口；
- 状态进度和所有 `can_*` 操作标记；
- 附件当前状态、下载和作废权限。

拆分依据：该域状态最多、角色最多，也是其他任务成果和申诉流程会重新进入的核心域。

### 9.3 学分兑换回归

- 可兑换课时记录和全部有效成员是否正确返回；
- 无当前生效规则时成员仍返回、但不可提交；
- 兑换规则生效区间和快照；
- 草稿、提交、指导老师确认和管理员终审；
- 批量终审的部分失败与事务行为；
- 课时扣减、学生学分记录和兑换记录的一致性。

拆分依据：事务调整最可能影响账户扣减和记录生成，必须确认不会重复扣减或部分成功。

### 9.4 申诉回归

- 可申诉对象和不可重复申诉限制；
- 管理员受理或拒绝；
- 指导老师再次确认；
- 管理员重新分配审核老师；
- 审核老师复审；
- 管理员完成原业务终审后申诉同步完成；
- 申诉总状态和 `reopen_stage` 的前端展示。

拆分依据：申诉是跨域编排流程，服务依赖调整和事务统一最容易改变其行为。

### 9.5 学院任务与成果回归

- 管理员发布和指导老师申请发布；
- `registration_start_at` 自动生成；
- 报名截止前后边界；
- 截止前禁止筛选；
- 截止后任务推进到待筛选；
- 成员筛选和队长指定；
- 只有队长能够提交成果；
- 成果驳回后修改原主记录并新增版本；
- 当前附件与历史版本附件；
- 成果通过后自动课时申请状态和指导老师继承关系。

拆分依据：当前任务、成果、申诉和投诉位于同一服务文件，拆开时容易遗漏内部调用或状态同步。

### 9.6 附件回归

- 上传后尚未绑定的可见性；
- 绑定草稿后的删除；
- 正式提交后的作废限制；
- 管理员作废原因；
- 不同业务对象的下载权限；
- 成果重提后历史附件和当前附件的区分；
- 规则文件附件是否仍可下载。

拆分依据：附件是跨域能力，抽取后所有业务都会受到影响。

### 9.7 导入导出与基础配置回归

- 学生、教师、管理员模板下载及导入；
- 教师角色标记和账号状态；
- 任务类型启停；
- 规则文件和结构化兑换规则；
- 课时申请导出字段、权限和文件格式。

### 9.8 推荐的前端回归方式

1. 后端先提供“重构前/重构后”典型接口响应对比。
2. 前端对 TypeScript 类型或字段映射执行静态检查。
3. 先测登录、列表、详情等只读接口。
4. 再按课时申请、兑换、任务、申诉的完整闭环测试。
5. 最后测试跨域附件、错误提示、重复操作和时间边界。
6. 每个失败项记录请求、响应、账号、前置状态和数据库状态，不只提供页面截图。

## 10. 按建议修改后可能出现的问题及应对方式

### 10.1 路由漏注册或 URL 改变

**表现：** 原接口突然 404，或 endpoint 名称变化影响 `url_for`。  
**原因：** 拆分蓝图时漏导入、漏注册、重复添加前缀。  
**控制：** 自动遍历 Flask `url_map`，将重构前后方法和路径做快照对比。

### 10.2 响应字段或类型无意变化

**表现：** 前端字段为 `undefined`，Decimal 由 number 变字符串，空数组变 `null`。  
**原因：** 抽取 schema 时重新定义了序列化方式。  
**控制：** 为关键接口保存契约样本并进行结构测试；前端同步运行类型检查。

### 10.3 错误码和 HTTP 状态变化

**表现：** 前端无法进入原来的提示或登录跳转逻辑。  
**原因：** 全局错误处理和业务异常处理合并时映射不一致。  
**控制：** 建立错误码清单，对 401/403/404/409/413 单独回归。

### 10.4 事务范围改变导致数据部分成功或全部回滚

**表现：** 操作日志存在但主记录失败，或以前部分成功的批量操作现在全部失败。  
**原因：** 从服务内部提交改为应用服务统一提交后，事务语义发生变化。  
**控制：** 先为现有事务行为补测试；明确批量操作采用全有全无还是逐条处理。

### 10.5 ORM Session 和延迟加载问题

**表现：** 提交后序列化关系字段时报 detached/lazy loading 错误。  
**原因：** DTO 组装位置移动到事务或 session 生命周期之外。  
**控制：** 在 session 有效期内构造 DTO；对详情查询明确加载策略。

### 10.6 查询次数增加和性能下降

**表现：** 列表接口出现 N+1 查询，响应变慢。  
**原因：** 拆分 serializer 后逐条访问关联对象。  
**控制：** 为关键列表记录查询数量，使用 `joinedload/selectinload`，保留分页。

### 10.7 循环导入

**表现：** 应用启动失败或部分模块初始化不完整。  
**原因：** 蓝图互相导入、领域服务相互调用。  
**控制：** 由应用服务负责跨域编排；公共异常和身份能力下沉到 core；业务域避免反向依赖 API。

### 10.8 旧页面与新 API 行为分叉

**表现：** API 页面正常，但旧服务端页面仍调用旧 service，状态不一致。  
**原因：** 只重构 `/api/v1`，没有确认传统蓝图使用情况。  
**控制：** 建立旧入口清单，决定适配、废弃或迁移；删除前先验证实际调用。

### 10.9 Legacy 状态或历史数据无法兼容

**表现：** 旧数据在新枚举中无法解析，列表或状态文案异常。  
**原因：** Python 枚举过早拒绝数据库中的历史值。  
**控制：** 先统计生产/验收库状态分布，提供兼容映射和数据迁移，再收紧约束。

### 10.10 状态转换过度集中形成新的“大文件”

**表现：** 所有业务状态又被放进一个全局状态机文件。  
**原因：** 把“统一”误解为“集中到一个位置”。  
**控制：** 每个业务对象维护自己的状态和转换，公共层只提供机制，不保存全部业务状态。

### 10.11 过度设计降低开发效率

**表现：** 一个简单查询需要跨越路由、DTO、应用服务、领域服务、Repository 等大量文件。  
**原因：** 为追求架构形式一次性引入过多层。  
**控制：** 只为复杂度真实存在的模块增加抽象；简单查询允许 route → query service → schema。

### 10.12 重构与 V2 功能同时进行导致问题难定位

**表现：** 测试失败时无法判断是移动代码造成，还是新需求逻辑造成。  
**原因：** 同一提交同时重构、改接口和加功能。  
**控制：** 结构重构与需求开发分提交、分阶段验收；每个阶段保持测试通过。

### 10.13 文档再次落后于代码

**表现：** 架构目录已经变化，但接口和状态文档仍描述旧实现。  
**原因：** 文档被视为开发结束后的补充工作。  
**控制：** 将文档、OpenAPI 和测试列入 Definition of Done，契约变更必须同一合并请求完成。

## 11. 推荐实施顺序与验收标准

### 11.1 推荐顺序

```text
完成 V1 前端检查
→ 冻结测试和接口基线
→ 抽取错误/身份/时间等公共能力
→ 按业务域拆 API 路由
→ 抽取 schema/serializer
→ 按业务域拆 service
→ 集中各域状态转换
→ 调整跨域事务
→ 处理旧入口和 legacy 数据
→ 引入 OpenAPI 与质量门禁
→ 开始 V2 新功能
```

### 11.2 每个阶段的完成标准

- 现有 25 项测试全部通过；
- 新增的结构风险有对应测试；
- `/api/v1` 方法、路径和权限保持不变，除非有书面契约变更；
- 关键接口请求和响应结构保持不变；
- 数据库迁移可以在空库和现有库执行；
- 完成该业务域的前端闭环回归；
- 文档和代码目录同步更新；
- Git 提交只包含当前阶段相关修改，能够独立回退。

### 11.3 是否需要立即重构

建议在 V1 前端最终检查完成并冻结版本后，先完成阶段 0 至阶段 2，再开始 V2 大量新增功能。原因是 API 大文件和按开发周组织的服务已经达到明显的维护临界点；继续追加功能仍能运行，但理解成本、冲突概率和回归范围会快速增加。

不建议在前端验收尚未结束时立即重构，也不建议一次性完成全部七个阶段。

## 12. 最终结论

1. V1 返工的核心原因是业务行为契约不完整，而不是简单的代码质量问题。
2. 数据库字段、主线流程和接口列表仍然必要，但还必须补充状态机、页面行为、错误语义、时间边界和异常场景。
3. 当前代码具备服务分层、数据库迁移和自动化测试基础，能够稳定支撑 V1，不需要推倒重写。
4. 当前最突出的结构风险是 API 大文件、按开发周命名的大型服务、新旧服务并存、状态与事务分散。
5. 最合理的治理方式是保持 V1 对外契约不变，按业务域渐进拆分，并在每一步执行自动化和前端闭环回归。
6. 架构调整后最需要前端重新验证的是响应结构、操作标记、状态展示、时间边界、附件、错误码及四条核心业务闭环。
7. V2 应把 OpenAPI、状态转换表、联调场景表和契约测试纳入开发完成标准，从流程上降低再次出现大规模理解偏差的概率。
